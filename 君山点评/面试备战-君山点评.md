## 四、核心亮点逐条讲法（面试官深挖时能展开）

### 1. 短信登录 + 双拦截器
- 验证码存 Redis（带 TTL），用户输对后生成 token 存入 Redis（value=用户对象，TTL 30min）。
- 用 **两个拦截器**：`LoginInterceptor` 校验 token 是否存在；`RefreshTokenInterceptor`（order=0，优先级最高）每次请求刷新 token 有效期，避免用户操作中间掉线。
- 用户信息用 `ThreadLocal`（UserHolder）在请求内传递，避免层层传参。

**追问应答**：为什么不存 session？→ 集群/分布式下 session 不共享，Redis 集中存更合适。

### 2. 商户缓存（缓存三件套，必考题）
- **穿透**（查不存在的 key）：缓存空值（null）并设置短 TTL，防止恶意轰炸 DB。
- **击穿**（热点 key 过期瞬间高并发）：**互斥锁**（setnx 抢锁，抢到的人查 DB 回写，其余自旋等待）——你代码里 `ShopServiceImpl` 用的就是 `queryWithMutex`。也实现了**逻辑过期**方案（`CacheClient.queryWithLogicalExpire`，不阻塞、异步重建）作为备选。
- **雪崩**（大量 key 同时过期）：TTL 加随机值，错开过期时间。

### 3. 分布式锁（你项目里有两套，讲手写那套最加分）
- **手写 `SimpleRedisLock`**：
  - 加锁：`SET key value NX`（value = `UUID-线程ID`，标识持有者）。
  - 解锁：用 `unlock.lua` 脚本保证「判断 value == 自己 → 再删除」的**原子性**，防止误删别人的锁。
  - 解决了三个基础问题：原子加锁、防误删、可重入可加超时。
- **Redisson**：秒杀链路里用的是 `redissonClient.getLock("lock:order:"+userId)`，`tryLock()` 默认走**看门狗**自动续期（30s），不用手动管过期。

**追问应答**：手写锁 vs Redisson 怎么选？→ 手写锁用于理解原理、面试展示；生产用 Redisson，它解决了可重入、自动续期、红锁（多节点）等问题。

### 4. 秒杀（你项目的重头戏，讲这条主线）
⚠️ **先看清你代码真正生效的链路**（别讲错）：

```
前端请求
  → seckillVoucher()
  → 执行 seckill.lua（Redis 内原子完成：查库存 → 查一人一单(set) → 扣库存 → 记录已购用户）
  → Java 把订单消息发到 RabbitMQ（交换机 X，路由到队列 QA）
  → 前端立即拿到 orderId（异步，不阻塞）
  → SeckillVoucherListener 消费 QA（及死信 QD）
  → 落库订单 + 扣减 DB 库存（where stock>0 防超卖）
```

**关键点**（照着讲，自洽且专业）：
- **为什么用 Lua？** 判断库存、判断一人一单、扣库存这三步必须原子，否则高并发下会超卖。Lua 在 Redis 单线程里原子执行。
- **为什么异步？** 秒杀瞬时流量大，把「校验扣减」放 Redis（快），把「写 DB 订单」丢给 RabbitMQ 异步消费，削峰填谷，保护数据库。
- **怎么防超卖？** 两层：Redis Lua 预扣 + DB 层 `update stock=stock-1 where stock>0`（乐观约束兜底）。
- **一人一单？** Redis 用 set 记录已购用户（Lua 内 sismember 判断），DB 层再 `count` 复核。

🚨 **面试避坑提醒**（非常重要）：
- 你 `seckill.lua` 脚本末尾有一句 `XADD stream.orders`（往 Redis Stream 发消息）——这是**历史残留、实际没走 Stream**，别提 Redis Stream，就讲 RabbitMQ 异步落库这条线。
- `handleVoucherOrder` / `createVoucherOrder` 里那段 `proxy` 调用是**旧同步方案的注释残留**（proxy 实际未赋值），面试也**别提**，就讲「Redis 预扣 + MQ 异步落库」。

### 5. 其他 Redis 数据结构（被问「还用过 Redis 什么」时甩出来）
- **GEO**：附近商户（`GEOADD`/`GEORADIUS`），按经纬度搜周边。

## 五、高频八股 Q&A（直接背答案）

**Q1：缓存穿透/击穿/雪崩的区别和解决方案？**
A：穿透=查不存在的数据，每次打 DB → 缓存空值/布隆过滤器；击穿=单个热点 key 过期瞬间并发打 DB → 互斥锁/逻辑过期；雪崩=大量 key 同时过期 → TTL 加随机值+Redis 高可用。

**Q2：分布式锁怎么实现？你们项目用哪种？**
A：基于 Redis 的 `SET NX`。我们手写了一版（value 带 UUID-线程ID + Lua 原子解锁），秒杀里实际用 Redisson（看门狗自动续期）。Redisson 还解决可重入和红锁问题。

**Q3：Redisson 看门狗是什么？**
A：`tryLock()` 不传leaseTime 时，锁默认 30s，看门狗每 1/3 时间（10s）自动续期，直到业务执行完主动 unlock，避免业务没跑完锁就过期。

**Q4：秒杀怎么防止超卖？**
A：两层防护。Redis 层用 Lua 脚本原子地完成「查库存+扣库存+记录用户」；DB 层用 `update stock=stock-1 where stock>0` 兜底。库存预存在 Redis，下单走异步落库削峰。

**Q5：为什么用 Lua 脚本？**
A：Redis 单线程执行 Lua，脚本内多步操作对外部是原子的，避免「查库存」和「扣库存」之间被其他线程插空导致超卖。

**Q6：Redis 和 MySQL 数据一致性怎么保证？**
A：读多写少场景用 Cache-Aside：读时缓存没有则查 DB 回写；写时**先更新 DB、再删除缓存**（删除优于更新，避免并发下写脏）。我们项目商户缓存以读为主，更新走删缓存。

**Q7：RabbitMQ 在秒杀里起什么作用？为什么不直接写库？**
A：削峰填谷。秒杀瞬时 QPS 高，Redis 扛住校验和预扣，订单消息进 MQ 由消费者匀速落库，保护 MySQL 不被冲垮；同时前端秒级拿到 orderId 提升体验。

**Q8：RabbitMQ 怎么保证消息不丢？**
A：生产者 confirm 机制、队列/消息持久化、消费者手动 ACK。我们用了 QA 队列 + 死信队列（QD）做异常处理兜底。

**Q9：Redis 为什么快？**
A：纯内存、单线程避免锁竞争、IO 多路复用（epoll）、高效数据结构。

**Q10：你们缓存更新策略，为什么不用逻辑过期所有场景？**
A：逻辑过期不阻塞、性能好，但要保证数据最终一致、且有重建开销；热点 key 用互斥锁更稳，普通 key 用逻辑过期，按场景选。

## 六、高并发秒杀平台补充（辅项目，被问异步/消息队列时讲）

- **架构**：下单请求 → 校验 → 发 RabbitMQ（**direct 交换机 X/Y**，路由键打到队列 **QA/QD**）→ 消费者异步创建订单。
- **死信队列（QD）**：QA 消费失败/超时的消息进死信路由，保证订单不丢、可重试。
- **Redis 角色**：缓存库存、用 `setnx` 做分布式锁防重复下单、扛击穿。
- **一句话**：用消息队列把「同步下单」改成「异步削峰」，DB 只在自己节奏下处理，系统吞吐量上去了。
