## 一、登录与会话

**Q1：短信登录怎么做的？验证码和 token 存哪？**
A：验证码发到手机后，把 code 存 Redis（key=手机号，TTL 5 分钟）。用户提交验证码，比对 Redis 里的 code，对了就生成 token（随机串），把 token→用户信息(JSON) 也存 Redis（TTL 30 分钟），token 返给前端存本地。后续请求头带 token，拦截器校验。
你项目：`UserServiceImpl` 发码/校验，`LoginInterceptor` 拦截需登录的接口，`UserHolder`（ThreadLocal）在请求内传递用户。

**Q2：为什么用双拦截器（Login + RefreshToken）？**
A：`LoginInterceptor` 只校验"有没有 token、对不对"，没 token 直接拦；`RefreshTokenInterceptor`（order=0，最先执行）每次请求都刷新 Redis 里 token 的 TTL，避免用户一直操作却因 30 分钟不动被踢。两个职责分开，逻辑更清晰。

**Q3：用户信息怎么在 Controller/Service 间传？**
A：登录校验通过后把用户对象塞进 `ThreadLocal`（UserHolder），任何地方 `UserHolder.getUser()` 直接取，请求结束 `afterCompletion` 里 remove 防内存泄漏。比传参优雅，也避免序列化开销。

**追问：ThreadLocal 为什么用完要 remove？**
A：线程池线程复用，不 remove 会串号（下一个请求读到上一个用户），而且内存泄漏。必须 try-finally/afterCompletion 清理。

## 二、商户缓存（Redis）

**Q4：商户信息怎么用缓存？缓存和 DB 怎么一致？**
A：Cache-Aside。查的时候先查 Redis，没有再查 MySQL，回写 Redis。更新商户时**先改 DB、再删缓存**（删比更新安全，避免并发写脏）。读多写少场景，不一致窗口极小。
你项目：`ShopServiceImpl.queryWithMutex` 走的就是这个模式，缓存 key=`cache:shop:`+id。

**Q5：缓存穿透怎么解决的？**
A：恶意查不存在的 id，每次穿透打到 DB。方案：缓存空值（null）设短 TTL；更彻底用布隆过滤器。你项目用的是**缓存空值**（对不存在的 key 也写个空标记）。

**Q6：缓存击穿（热点 key 过期瞬间）怎么防？**
A：互斥锁——第一个线程发现缓存没，用 `setnx` 抢锁，抢到的查 DB 回写，其余线程自旋/短暂等待重试。你项目 `ShopServiceImpl` 的 `queryWithMutex` 就是这个实现。备选还有逻辑过期（CacheClient.queryWithLogicalExpire，不阻塞、异步重建）。

**Q7：缓存雪崩怎么防？**
A：大量 key 同时过期会集中打 DB。给 TTL 加随机值错开；再就是 Redis 高可用（哨兵/集群）兜底。

**Q8：附近商户怎么查的？用了什么结构？**
A：Redis 的 **GEO**。商户经纬度 `GEOADD` 进 set，查询时用 `GEORADIUS`/`GEOSEARCH` 按距离半径搜，返回附近商户+距离，按距离排序展示。你项目 `ShopServiceImpl` 里有 GEO 查询逻辑。

## 三、分布式锁

**Q9：你们项目里的分布式锁是怎么实现的？**
A：两套。① **手写 `SimpleRedisLock`**：加锁 `SET key UUID-线程ID NX`（UUID 标识持有者，防误删）；解锁用 `unlock.lua` 脚本保证"判断 value 是自己 → 删除"原子，避免删了别人的锁。② **Redisson**：秒杀里用 `redissonClient.getLock("lock:order:"+userId)`，默认看门狗自动续期。

**Q10：手写锁为什么 value 要带 UUID + 线程ID？**
A：只靠 key 无法区分是哪个线程/实例加的锁。如果 A 加锁后业务卡顿锁过期，B 抢到，A 恢复后直接 delete 会把 B 的锁删了。value 存"UUID-线程ID"，解锁时比对 value 一致才删，解决误删。

**Q11：为什么解锁要用 Lua？**
A：解锁是"读 value → 判断 → 删"，两步非原子。中间被插空就可能误删别人锁。Lua 在 Redis 单线程里原子执行，杜绝该问题。

**Q12：Redisson 看门狗是什么？**
A：`tryLock()` 不传 leaseTime 时锁默认 30s，看门狗每 10s（1/3）自动续期，直到业务跑完主动 unlock。省去手动算过期时间，防止业务没结束锁先失效。

**Q13：Redisson 锁还解决了手写锁哪些短板？**
A：可重入（Hash 记录重入次数）、自动续期、支持红锁（RedLock，多 Redis 主节点，防单点故障）。手写锁想做可重入和红锁都很麻烦。

## 四、秒杀（重头戏）

**Q14：秒杀整体链路怎么设计的？**
A：请求 → 执行 `seckill.lua`（Redis 内原子完成：查库存、查一人一单、扣库存）→ 通过则把订单消息发 **RabbitMQ**（交换机 X，队列 QA）→ 前端立即拿到 orderId（异步不阻塞）→ `SeckillVoucherListener` 消费消息 → 落库订单 + 扣减 DB 库存。
你代码：`VoucherOrderServiceImpl.seckillVoucher` + `seckill.lua` + `SeckillVoucherListener`。

**Q15：为什么用 Lua 脚本做库存扣减？**
A：判断库存、判断一人一单、扣库存这三步必须原子，否则并发下会超卖。Redis 单线程执行 Lua，整段对外部原子，杜绝中间被插空。

**Q16：怎么防止超卖？**
A：两层。① Redis Lua 预扣，库存不足直接返回，不进下单流程；② DB 落库时用 `update stock=stock-1 where voucher_id=? and stock>0` 乐观约束兜底，库存真不够就更新失败。

**Q17：怎么保证一人一单？**
A：Redis 用 set 记录已购用户（Lua 里 `sismember` 判断），同一用户第二次请求直接拒绝。DB 层再 `count` 复核一次。

**Q18：为什么用 MQ 异步落库，不直接写 DB？**
A：秒杀瞬时 QPS 极高，Redis 扛校验和预扣（快），订单写 DB 丢给 MQ 由消费者匀速处理，削峰填谷保护 MySQL，前端也能秒级返回 orderId 提升体验。

**Q19：MQ 怎么保证订单不丢？**
A：生产者 confirm 机制确认投递、队列和消息持久化、消费者手动 ACK。你项目用了 QA 队列 + **死信队列 QD**，消费异常/超时的消息进死信路由，可重试不丢单。

🚨 **避坑（和上次备战包一致）**：你 `seckill.lua` 末尾那句 `XADD stream.orders` 是历史残留、实际没走 Redis Stream；`handleVoucherOrder`/`createVoucherOrder` 里的 `proxy` 调用也是注释残留。**面试只讲 RabbitMQ 异步落库主线**，别提 Stream。

## 五、关注与 Feed 流

**Q20：关注和粉丝列表用什么存？**
A：Redis **ZSet**（有序集合），score 用时间戳。关注/取关就是 `zadd`/`zrem`，查列表按时间倒序 `reverseRange`。你项目 `FollowServiceImpl` 里有实现。

**Q21：探店笔记的 Feed 流怎么做分页？**
A：用 ZSet 按时间戳排序，采用**游标分页**（记下上一页最后一条的 score/timestamp，下一页查 `score < lastScore` 取 N 条），避免传统 limit offset 在Feed频繁更新时的重复/漏读问题。你项目 `BlogServiceImpl` 有 Feed 查询。

**追问：推模式还是拉模式？**
A：你项目偏拉模式（关注的人多时查各关注者的最新笔记聚合）。推模式是发笔记时直接推给所有粉丝的收件箱，粉丝多看写入压力大。大厂一般推拉结合。

## 六、签到（BitMap）

**Q22：签到功能怎么存？为什么不用一张表？**
A：Redis **BitMap**。一年 365 天就是 365 个 bit，`SETBIT` 标记某天签到，`BITCOUNT` 统计总签到天数，`BITFIELD` 还能算连续签到。比 MySQL 一行一天省几个数量级空间，统计极快。你项目 `UserServiceImpl` 里有 BitMap 签到逻辑。

## 七、事务与 MySQL

**Q23：一人一单的落库为什么用事务？**
A：`createVoucherOrder` 里先 `count` 查是否已购，再扣库存、再 `save` 订单，这几步必须原子，否则并发下两个请求都查到"未购"然后都下单。用 `@Transactional` 包住，且 DB 层 `where stock>0` 兜底防超卖。

**Q24：扣库存那句 SQL 为什么写 `stock=stock-1 where stock>0`？**
A：这是乐观锁思路，不在应用层先查后减（有并发窗口），而是让 DB 在更新时判断库存仍大于 0 才扣，返回影响行数 0 即代表已抢光。原子且安全。

## 八、拓展八股（被问到原理时答，别硬说项目用过）

**Q25：UV 统计用什么？**
A：【拓展】海量 UV 用 Redis **HyperLogLog**，12KB 内存估上亿去重，误差 ~0.81%。**你项目目前没实现 UV 统计**。被问就说"原理清楚、标准用 HLL，我们这版用户量没到那个量级，就先没接"。

**Q26：缓存和 DB 一致性还有更强方案吗？**
A：延迟双删、Canal 订阅 binlog 异步删缓存、读写穿透（Read/Write Through）。Cache-Aside 已够大部分场景，更强方案牺牲复杂度换一致性。

**Q27：Redis 为什么单线程还这么快？**
A：纯内存、单线程无锁竞争、IO 多路复用（epoll）、高效数据结构。6.0 后有多线程 IO 但命令执行仍单线程。

**Q28：Redis 持久化知道吗？**
A：RDB（快照，恢复快、丢数据多）+ AOF（命令日志，丢数据少、文件大）。生产常混合用。我们项目重启丢缓存无所谓，因为能回源 DB 重建。
